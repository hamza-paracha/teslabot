# OAuth operations

1. Deploy and verify the public key, complete Tesla registration, enter credentials through the local hidden-input setup script, upload secrets after approval.
2. Register the partner using `npm run partner`, with TESLABOT_URL and TESLABOT_ADMIN_TOKEN securely provided in the local environment. The script calls the protected Worker; credentials/token generation remain server-side.
3. Open your deployed HTTPS dashboard and authenticate using the local administrator credential: the value of `ADMIN_TOKEN` in your private `.dev.vars` file, without surrounding quotes. This is not your Tesla password. Click Connect Tesla Account, or Reconnect Tesla Account if already connected. Sign into the VEHICLE account in Tesla's official page, which may differ from the developer account. The authorization request includes `prompt=login` to request a fresh sign-in. If the browser still selects the wrong account, start the entire dashboard flow in a private browser window.
4. Approve requested read-only scopes. The callback must match exactly. A denial, missing code, expired/replayed state or wrong browser fails closed. Start again from the dashboard if the transaction expires.
5. A successful browser callback returns to the dashboard and performs one account-metadata discovery. Inspect display names/states, choose the correct vehicle and click Select vehicle. No automatic selection occurs, even if there is one vehicle. Load vehicles / Reload vehicles explicitly checks Tesla again, bypassing the five-minute metadata cache. Click Refresh Vehicle Data only when desired. An asleep vehicle is not woken; wait until naturally awake or use the official Tesla app yourself.
6. Disconnect deletes local owner tokens, selection, caches, OAuth transactions and sessions. It also signs you out of the dashboard: enter the administrator credential again before reconnecting. Also revoke teslabot in Tesla account third-party app management to invalidate the grant at Tesla. Local deletion alone does not invalidate previously issued Tesla tokens.

Reconnection requires an administrator session and a same-origin POST. It keeps the current connection while the owner signs in. Denial, expiry or failed token exchange leaves the current connection intact. A successful replacement clears old selection, caches, history, observation preferences, other pending OAuth attempts and browser sessions, then opens a new dashboard session. Explicitly select the vehicle again. This does not revoke the previous grant at Tesla.

An empty list is a successful discovery with no authorized vehicles, not proof of a particular wrong account or missing permission. Check that the account shows the car in Tesla's app; review teslabot under Tesla Account Settings > Security > Third Party Apps and approve Vehicle Information and the intended vehicle. Tesla says permission changes can take a couple of hours to sync. Reconnect if needed, then reload. The dashboard reports whether Vehicle Information appears in Tesla's returned scope; an omitted scope is shown as unknown, not missing. Account/profile identity permission is not requested.

Browser OAuth failures return to a dashboard message using a stable error code, without retaining the authorization code or state in the landing URL. API callers receive structured errors and recovery steps.

Tokens rotate server-side and remain encrypted; no access/refresh token is returned to a browser or MCP client. If scope, password or consent changes invalidate authorization, use Reconnect Tesla Account. D1 persists across deployments with the same binding; never casually replace its encryption secret. Apply migration `0002_oauth_purpose.sql` to the existing database before deploying this version; see [Cloudflare setup](CLOUDFLARE_SETUP.md).

Sources: [Tesla third-party tokens](https://developer.tesla.com/docs/fleet-api/authentication/third-party-tokens), [Tesla access management](https://www.tesla.com/support/access-third-party-apps).
