# Security review and threat model

Assets: Tesla credentials, owner/partner tokens, location/VIN, administrator sessions, private vehicle key and billing budget. Adversaries include public internet users, malicious websites, compromised MCP clients, prompt-injection content, and an attacker obtaining a database backup.

Controls implemented: static public shell only; protected data/administration; random separate admin/MCP credentials; browser-bound expiring single-use OAuth state; strict origin for browser POST; one-hour opaque secure cookies; no token URLs/localStorage; fixed Tesla regional hosts; credential-bearing redirects rejected; AES-256-GCM encrypted D1 records with authenticated record names; scoped MCP read-only access; bounded HTTP timeouts; serialized rotation and usage reservations; no wake, polling or command implementation; no console logging of upstream errors, credentials or vehicle data. Worker invocation observability is off to reduce OAuth-code query logging. Cloudflare account-level logs/WAF tools must also be reviewed for query-string retention before production.

Private key: generated locally, prime256v1, mode 0600, outside public/ and never imported by the Worker. Only the public PEM is an asset. Preserve this key; don't run keys again to rotate. Encrypt backups offline. No language-model interface can request the private key.

Database backups: use authenticated Cloudflare D1 export/restore and inspect the current recovery retention for the selected plan. Backups contain ciphertext but remain sensitive. Keep the encryption key separately in a password manager/offline encrypted backup; database-only recovery cannot decrypt tokens. Restoring old refresh tokens may require reauthorization because Tesla rotates them. Keep the same D1 database and secret across deployments. Revoke consent if backups or tokens may be compromised. Key rotation requires migration/re-encryption, not replacing the secret blindly.

Environment separation: use separate Worker names, D1 databases, secrets and Tesla registration for staging. Local .dev.vars and .wrangler state are ignored. No remote staging/live database testing. No user secrets in committed files. Production configuration has no workers.dev route or scheduled tasks.

Rate limiting: 120 authenticated HTTP requests/minute per account, and 60/minute across the public sign-in and administrator-login entry points; request/spend reservations persist in D1. Cloudflare WAF/Access may be added after account inspection for stronger perimeter/rate controls. If adding Access, the public key must bypass it, and OAuth callback must remain accessible with state validation. Never trust an unsigned Cloudflare Access email header.

Residual limitations: bearer credential theft permits its granted access; use strong generated credentials, restrict local client files and rotate compromised credentials. The shared administrator token is a personal bootstrap mechanism, not multi-user identity/MFA. Tesla token refresh and D1 writes cannot be atomically committed across providers; storage failures can require reauthorization. The 120-second lease assumes bounded requests; overloaded requests can fail and must not be blindly retried. App counters are not invoice guarantees. Each installation requires its own cloud inspection and live OAuth/API verification. No independent penetration test has been performed.

Account disconnection removes local credentials/data and invalidates sessions. It does not promise server-side Tesla token revocation; revoke the grant in Tesla's own account interface. Back up private keys securely and manage partner registration separately.

Security-sensitive commands require an authenticated confirmation bound to vehicle, exact action/parameters, expiration and single-use challenge. MCP must not have access to approving those confirmations. Never enable commands on the strength of untrusted text.

Observation history is opt-in, encrypted with the same per-record authenticated encryption as tokens, capped at 48 samples and filtered to seven days. Pruning occurs on history reads and observation writes; inactive installations and backups can retain older ciphertext. Disabling history removes the stored history, while the two latest observations remain for comparisons. Disconnect removes history and preferences. MCP credentials cannot enable collection, change thresholds or change alert settings.

Accounts: the operator's `ADMIN_TOKEN` controls the installation. Drivers join only through single-use, expiring invites (stored as hashes) and authenticate with Tesla. The Tesla account identifier comes from the token response that Tesla sends directly to the Worker over TLS (OIDC Core 3.1.3.7). Only a SHA-256 hash of it is stored; the ID token is never persisted. Every record key is namespaced by account and is also the record's AES-GCM authenticated context, so ciphertext cannot be moved between accounts. Locks, usage, rate limits, sessions and MCP credentials (`tbm_`, stored as hashes, up to 10 per driver) are per account. Disabling an account ends its sessions and blocks its credentials and alerts immediately. Deleting it removes its records, credentials and telemetry configuration. The owner account cannot be bulk-deleted, because it shares unprefixed keys with installation records.

Fleet Telemetry: vehicle TLS terminates in Tesla's `fleet-telemetry` server inside the container (Spectrum passthrough), so the car's client certificate is verified there. The partner private key exists only as a secret in the telemetry Worker and container, where Tesla's proxy uses it. The relay exposes only the `fleet_telemetry_config` create call, behind `RELAY_TOKEN`. The ingest credential may only post records, and records are applied only to the account that enabled telemetry for that VIN and still has it selected.

Server-side alerts are off by default. Only the administrator can enable them and choose an https notification URL without embedded credentials. That URL often contains a secret topic, so it is stored encrypted, only its host is shown, and redirects are refused. A cron trigger runs every 10 minutes. It makes no Tesla request unless a plug-in check or briefing is due, never wakes the car, and stays within the normal daily/monthly budget. The MCP credential may write only trip plans, trip outcomes and briefing events, all stored encrypted. Briefing titles have control characters removed, are limited to 120 characters and are treated as display text only. Disconnecting deletes alert settings, briefings, alert state and trips.

`tesla_plan_departures` runs locally in the MCP host process using the host's authorized event and forecast inputs. It reads only cached vehicle data and stores no calendar inputs in D1. Event text is untrusted and cannot authorize actions. Notification delivery and schedules belong to the host and require explicit user settings. The portable plugin package contains no credential; its runtime reads a permission-restricted local MCP configuration. Proposed heating is always non-executable in this release.
